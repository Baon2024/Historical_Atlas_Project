# Validation notes

The implementation is checked with TypeScript, a Next.js production build, six data unit tests, and five Playwright browser scenarios using installed Google Chrome on Windows. Shared application state lives in `AppProvider` and is read or updated with `useAppContext()`. All historical JSON is statically imported at startup in `lib/demoData.ts`. A browser scenario blocks the historical-data URLs and exercises all six snapshots, checking that no requests are made to those URLs.

The chosen visual direction is a light atlas: warm ivory panels, green-gray ocean, pale land, dark readable text, serif headings, and stable polity colours. A generated 1536×1024 UI reference was inspected before implementation and retained at `.cache/design-reference.png`. Browser captures include that reference size, 1920×1080, and 375×667, with overview, inspector, and rotated globe states. The generated image is only a design reference; all map surfaces, typography, and controls are real components. No pixel-perfect match is claimed.

The initial interleaved overlay exhibited depth conflicts in screenshot review. The final overlaid integration removes those conflicts. A bundled Natural Earth world tile provides geographic context when external tiles cannot be fetched. Its generation clips polygons at the antimeridian to avoid seams. The local outline is coarse by design, so zoomed coastlines are angular.

The original CARTO raster provider is restored. Tile URLs take their `key` parameter from `NEXT_PUBLIC_CARTO_API_KEY` in `.env`. Without a configured key, the application keeps the local globe and displays setup instructions without making CARTO requests. Automated tests block CARTO requests to avoid spending the key's tile allowance; they cover the missing-key message or keyed-request failure path, and absence of direct OpenStreetMap tile requests. Live tile delivery requires a valid user-supplied CARTO key.

Before the change to static startup imports, a 10,000-coordinate stress probe recorded approximately 0.14 seconds to first contentful paint, 2.37 seconds to map ready, and 4.84 sampled animation frames per second during dragging. An ordinary three-polity run recorded 0.74 seconds to FCP and 2.65 seconds to map ready. These are historical software-rendering observations, not timings for the current import path. The network-injected stress test was removed alongside dataset fetching. Hardware-accelerated profiling is still required; the 60 FPS target has not been verified and the interactive-time target has not been consistently demonstrated.

Checks cover all registered startup datasets, all six dates without historical-data requests, direct map hover/picking, background dismissal, selection resets, mobile/reduced-motion behaviour, WebGL fallback, and failed external basemap tiles. The former dataset retry and stale-response checks were removed because historical data is no longer fetched.

The test runner writes ordinary startup measurements into `.cache/qa/normal-performance.json`; repeated runs vary with software-renderer load. An existing `.cache/qa/performance.json`, if present, is an earlier stress-run artifact. The final handoff reports functional checks separately from unverified performance targets.
